Core Chains — Warm-Up

If these feel slow, everything below will feel much harder than it needs to
Question 1

Given a List<String> of words, return a comma-separated string of all words longer than 4 characters, in uppercase, sorted alphabetically.

▸ Show solution 
String result = words.stream()
    .filter(w -> w.length() > 4)
    .map(String::toUpperCase)
    .sorted()
    .collect(Collectors.joining(", "));
Why this order: Filter before map — reduces the working set before doing the (slightly) more expensive uppercase transform on every remaining element. Small on a short list, but it's the correct default habit for larger pipelines: narrow first, transform second.
Question 2

Given a List<Integer>, find the sum of squares of all even numbers, without a traditional for-loop.

▸ Show solution 
int sumOfSquares = numbers.stream()
    .filter(n -> n % 2 == 0)
    .mapToInt(n -> n * n)
    .sum();
Why mapToInt, not map: map on a Stream<Integer> would give you a Stream<Integer> back, requiring unboxing overhead and no direct .sum(). mapToInt converts to an IntStream — a primitive specialization avoiding autoboxing entirely, with .sum() built in. This distinction (object stream vs primitive stream) is a very common thing interviewers check for.

Grouping & Partitioning

The pattern behind most real-world "aggregate this data" interview questions
Question 3

Given a List<Employee> (with department and salary fields), group employees by department, and for each department compute the average salary — result should be a Map<String, Double>.

▸ Show solution 
Map<String, Double> avgSalaryByDept = employees.stream()
    .collect(Collectors.groupingBy(
        Employee::getDepartment,
        Collectors.averagingDouble(Employee::getSalary)
    ));
The pattern: groupingBy takes a classifier function and a downstream collector — that second argument is the part people forget exists. Without it, you'd get Map<String, List<Employee>> and need a second pass to compute averages. Passing averagingDouble as the downstream collector does the aggregation in the same single pass.
Question 4

Given the same employee list, produce a Map<String, Long> of department → count of employees earning above $100,000.

▸ Show solution 
Map<String, Long> highEarnerCountByDept = employees.stream()
    .filter(e -> e.getSalary() > 100_000)
    .collect(Collectors.groupingBy(
        Employee::getDepartment,
        Collectors.counting()
    ));
Trap to watch for: Filtering before grouping here is correct because we want counts of the filtered set, per department. If instead you needed "for every department, how many earn above 100k, including departments with zero" you'd need to group first, then filter within each group — filtering before grouping silently drops departments with zero matches from the result map entirely.
Question 5

Split a List<Integer> into two groups: even and odd, as a Map<Boolean, List<Integer>>.

▸ Show solution 
Map<Boolean, List<Integer>> partitioned = numbers.stream()
    .collect(Collectors.partitioningBy(n -> n % 2 == 0));
// partitioned.get(true) -> evens, partitioned.get(false) -> odds
partitioningBy vs groupingBy: Use partitioningBy specifically for a boolean predicate — it always returns exactly two keys (true/false), even if one group is empty, unlike groupingBy which only creates keys that actually occur. Reaching for groupingBy(predicate) instead of partitioningBy is a common "it works but shows you don't know the more precise tool" tell.

flatMap

The operation most candidates can define but can't apply under pressure
Question 6

Given a List<List<Integer>> (a list of lists), return a single flat, deduplicated, sorted List<Integer>.

▸ Show solution 
List<Integer> result = nestedLists.stream()
    .flatMap(List::stream)
    .distinct()
    .sorted()
    .collect(Collectors.toList());
Why flatMap, not map: map(List::stream) would give you a Stream<Stream<Integer>> — a stream of streams, which isn't directly usable. flatMap takes each inner stream and merges all their elements into one single flat stream. Rule of thumb: if your mapping function itself returns a stream/collection and you want one merged result, you need flatMap, not map.
Question 7

Given a List<Order> where each Order has a List<LineItem>, find all unique product names across every order.

▸ Show solution 
Set<String> uniqueProducts = orders.stream()
    .flatMap(order -> order.getLineItems().stream())
    .map(LineItem::getProductName)
    .collect(Collectors.toSet());
Real-world shape: This exact pattern — flatten a one-to-many relationship, then map to the field you actually need — is the most common practical use of flatMap. It shows up constantly: orders→line items, customers→addresses, departments→employees→skills.

Custom Collectors

Pro-level territory — most candidates have never had to write one
Question 8

Write a custom Collector that joins a stream of strings with a comma, but wraps the final result in square brackets — without using Collectors.joining(", ", "[", "]") (which does exist and is the real answer for this specific case — but implement it manually to demonstrate you understand the Collector interface).

▸ Show solution 
Collector<String, StringBuilder, String> bracketJoin =
    Collector.of(
        StringBuilder::new,                          // supplier: new accumulator
        (sb, s) -> {                                  // accumulator: add one element
            if (sb.length() > 0) sb.append(", ");
            sb.append(s);
        },
        (sb1, sb2) -> {                                // combiner: merge two accumulators
            if (sb1.length() > 0 && sb2.length() > 0) sb1.append(", ");
            return sb1.append(sb2);
        },
        sb -> "[" + sb + "]"                           // finisher: transform to final result
    );

String result = words.stream().collect(bracketJoin);
The four parts of a Collector: Supplier creates a fresh mutable container per (potentially parallel) chunk. Accumulator folds one element into that container. Combiner merges two containers together — this is what makes parallel streams possible, since each thread accumulates its own container and combiner merges results. Finisher transforms the final container into the actual result type. Understanding the combiner's role is usually the part that separates "recited the definition" from "actually gets it."

Parallel Stream Pitfalls

The question that separates people who've read about streams from people who've been burned by them
Question 9

What's wrong with this code, and how would you fix it?

List<Integer> results = new ArrayList<>();
numbers.parallelStream()
    .forEach(n -> results.add(n * n));  // BUG
▸ Show solution

This is a classic race condition — ArrayList is not thread-safe, and multiple threads calling .add() concurrently during a parallel stream can corrupt internal state, silently drop elements, or throw ArrayIndexOutOfBoundsException. The fix is to never mutate shared external state from inside a stream operation — use collect instead, which is specifically designed to be parallel-safe:

List<Integer> results = numbers.parallelStream()
    .map(n -> n * n)
    .collect(Collectors.toList());
The general rule: Stream operations should be side-effect-free. The moment a lambda inside map/forEach/filter mutates something outside the stream (a shared list, a counter, an external variable), you've introduced a race condition the instant that stream runs in parallel — and it can even bite you in sequential streams if the same collection is touched elsewhere concurrently.
Question 10

When would you actually reach for .parallelStream() in production, and when would you specifically avoid it?

▸ Show solution
Reach for it whenThe dataset is large, the per-element work is genuinely CPU-intensive, and the operation is stateless/side-effect-free — parallel streams use the common ForkJoinPool, so real gains require real per-element cost to outweigh the splitting/merging overhead.
Avoid it whenThe dataset is small (overhead exceeds benefit), the operation involves I/O (blocking calls exhaust the shared ForkJoinPool used by all parallel streams app-wide, including unrelated ones), or ordering matters and hasn't been explicitly preserved.
The I/O trap specifically: All parallel streams in a JVM share the same common ForkJoinPool by default. A parallel stream doing blocking I/O (a DB call, an HTTP call per element) can starve that shared pool, silently degrading unrelated parallel streams running elsewhere in the same application — this is a genuinely dangerous, hard-to-diagnose production issue, not a theoretical concern.

Advanced Combinators

reduce, Collectors.teeing, and knowing when NOT to use a stream at all
Question 11

Using reduce, find the longest string in a List<String> — without using Collectors.maxBy or .max().

▸ Show solution 
Optional<String> longest = words.stream()
    .reduce((a, b) -> a.length() >= b.length() ? a : b);
Why Optional: The no-seed-value overload of reduce returns Optional<T> because the stream might be empty — there'd be no "longest" to return. This is a common thing candidates get wrong: forgetting reduce without an identity value must handle the empty-stream case, and Optional is how the API forces you to.
Question 12

Compute both the sum and the average of a List<Integer> in a single pass, without iterating the list twice.

▸ Show solution 
var result = numbers.stream()
    .collect(Collectors.teeing(
        Collectors.summingInt(Integer::intValue),
        Collectors.averagingInt(Integer::intValue),
        (sum, avg) -> Map.of("sum", sum, "average", avg)
    ));
Why this is genuinely pro-level: Collectors.teeing (Java 12+) runs two collectors over the same stream in a single pass and combines their results — most candidates' first instinct is to call .stream() twice (once for sum, once for average), which works but iterates the source twice unnecessarily. Knowing teeing exists is a strong signal of staying current with the Collectors API beyond the Java 8 basics.
Question 13

When would you deliberately choose a plain for-loop over a stream, even though a stream could technically do the job?

▸ Show solution

Three legitimate reasons: (1) Early exit with complex state — a loop with a `break` and multiple accumulated variables is often clearer than contorting a stream to short-circuit correctly. (2) Genuine readability — a deeply nested, multi-stage stream pipeline can become harder to read than an equivalent loop, especially for someone unfamiliar with the codebase; clarity should beat "used a stream" as a goal. (3) Checked exceptions — lambdas inside streams can't throw checked exceptions cleanly, forcing awkward try-catch-wrap-in-unchecked patterns that a plain loop avoids entirely.

Say this in interview: "I don't treat streams as strictly superior to loops — I reach for them when they make the transformation pipeline more readable and the operations are naturally side-effect-free. A loop is still the right tool when there's complex early-exit logic, checked exceptions in play, or when a stream chain would genuinely hurt readability for the next person touching this code."

Common Gotchas — Rapid Fire

Can you reuse a stream after a terminal operation (like collect or forEach) has run?
No — a stream can only be consumed once. Calling another operation on an already-consumed stream throws IllegalStateException. If you need to process the same data twice, re-create the stream from the source collection.
Are intermediate operations (map, filter) executed immediately when called?
No — streams are lazy. Intermediate operations only run when a terminal operation (collect, forEach, reduce, etc.) is invoked, and elements are processed one at a time through the whole pipeline, not stage by stage across the whole collection.
What happens if you call .peek() and expect it for side-effect logic?
peek() is meant for debugging/inspection, not for driving actual application logic — and if there's no terminal operation, or if the JVM optimizes the pipeline, peek's side effects may not even run as expected. Don't rely on it for anything beyond debugging.
groupingBy's downstream Map implementation — can you rely on iteration order?
No — the default groupingBy returns a HashMap, with no guaranteed order. Use groupingBy with a TreeMap::new supplier (the 3-arg overload) if you need sorted keys.
