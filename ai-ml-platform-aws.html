SageMaker vs Bedrock — Build vs Consume

The first architectural fork in almost every AI platform decision
Amazon BedrockManaged access to foundation models (Claude, Titan, Llama, others) via API — no infrastructure to manage, no model training. Includes Knowledge Bases (managed RAG), Agents (managed tool-calling orchestration), and Guardrails (managed content filtering) as built-in platform capabilities.
Amazon SageMakerThe full ML platform — train custom models from scratch, fine-tune open-source models, host your own inference endpoints, run notebooks, manage the entire ML lifecycle. Far more control, far more operational ownership.
Analogy: Bedrock is renting a fully-serviced apartment — furnished, maintained, you just move in and live. SageMaker is buying land and building a house — total control over the design, but you own the plumbing, the roof, and every repair.
Why this decision matters at platform-lead level

This isn't a one-time choice — most mature AI platforms end up using both, deliberately: Bedrock for the majority of GenAI use cases where a foundation model API is sufficient (chat interfaces, summarization, RAG-based Q&A), and SageMaker specifically where you need a custom-trained model, a fine-tuned open-source model at scale, or full control over training data lineage for compliance reasons.

Trade-off
Default to Bedrock whenA foundation model's general capability, possibly augmented with RAG, meets the requirement — fastest time to production, lowest operational burden, built-in governance tooling.
Reach for SageMaker whenYou need a model trained on proprietary data from scratch, fine-tuning at a scale/cost point Bedrock's managed fine-tuning doesn't fit, or full infrastructure control for regulatory/data-residency reasons.
Say this in interview

"My default architectural stance is Bedrock-first — it gets teams to production fastest with governance built in, and most GenAI use cases don't actually need a custom-trained model. I'd bring SageMaker in specifically where there's a real requirement Bedrock can't meet, not as a default platform choice, because the operational ownership cost is real and should be justified by an actual need."

MLOps Pipeline

CI/CD, but for models and data, not just code

Define: The discipline of applying software engineering rigor (versioning, automated testing, CI/CD, monitoring) to the ML lifecycle — training data, model artifacts, and deployed inference endpoints — because models drift and decay in ways application code doesn't.

Analogy: Regular CI/CD ships code that behaves the same way every time it runs, given the same input. MLOps has to account for a "correct" model from six months ago silently becoming wrong today, not because anyone changed the code, but because the real-world data it's scoring against has quietly shifted — like a tailor's measurements slowly going stale as a client's body changes, even though the suit pattern itself never changed.
The pieces beyond standard CI/CD
  • Model Registry — versioned, governed storage of trained model artifacts, with lineage back to the training data and code that produced them (SageMaker Model Registry). Answers "which exact model is in production, and what produced it" — essential for audit and rollback.
  • Feature Store — a centralized, consistent source of features used both for training and real-time inference, preventing training/serving skew (a model trained on one feature computation and served with a subtly different one — a very common, hard-to-debug production bug).
  • Model Monitoring / Drift Detection — tracking whether the live data distribution has drifted from training data, and whether model performance (accuracy, latency) is degrading — triggering retraining pipelines automatically when thresholds are crossed.
  • Automated Retraining Pipelines — SageMaker Pipelines (or Step Functions orchestrating the same idea) — a defined, versioned, repeatable sequence: pull fresh data → retrain → evaluate against a held-out set → promote to production only if it beats the current model on defined metrics.
Trade-off
Invest in full MLOps whenModels are business-critical, retrained regularly, and a silent performance regression would cause real damage.
Lighter-weight is fine whenEarly-stage experimentation, low-stakes models, or models that genuinely don't need frequent retraining — full MLOps tooling is real infrastructure investment that should match the model's actual business criticality.
Say this in interview

"The thing that makes MLOps genuinely different from standard CI/CD is that a model can go wrong without any code changing at all, purely because the world moved and the model didn't — that's why monitoring for drift and having an automated, metric-gated retraining pipeline matter as much as the initial training pipeline itself."

Vector Stores

The retrieval infrastructure underneath every RAG system

Define: A database optimized for storing high-dimensional vectors (embeddings) and finding the nearest neighbors to a query vector — the infrastructure that makes "find documents semantically similar to this question" fast at scale.

AWS options, and when each fits
Amazon OpenSearch (with k-NN)The most common choice for production RAG at scale — combines traditional keyword search with vector similarity search (hybrid search), which in practice out-performs pure vector search alone for many real-world queries.
pgvector on Amazon RDS/AuroraAdds vector search directly to Postgres — the pragmatic choice when your data already lives in Postgres and you don't want to stand up and operate a separate specialized system for moderate scale.
Amazon Bedrock Knowledge BasesFully managed RAG — handles chunking, embedding, storage, and retrieval as one managed capability, backed by OpenSearch Serverless or Aurora under the hood. Fastest to stand up, least operational control.
Analogy: A vector store is a librarian who's read every book and organized them not alphabetically, but by meaning — ask for "books about betrayal" and she can point you to relevant titles even if the word "betrayal" never appears on their covers, because she's indexed on concept similarity, not keyword matching.
Trade-off
Managed (Bedrock KB)Fastest time to value, least operational burden — right default for most teams starting out.
Self-managed (OpenSearch/pgvector)Needed when you require fine-grained control over chunking strategy, hybrid search tuning, or you're already operating that infrastructure for other purposes and don't want a second system.
Say this in interview

"I'd start with Bedrock Knowledge Bases as the default for most RAG use cases — it removes the operational burden of standing up and tuning a vector store. I'd move to self-managed OpenSearch specifically once a team needs fine control over chunking or hybrid search relevance tuning that the managed layer doesn't expose."

IaC for AI Infrastructure

Reproducibility matters more for AI infra than almost anywhere else

Define: Defining AI/ML infrastructure — SageMaker endpoints, Bedrock guardrail configurations, vector store clusters, IAM roles scoping model access — declaratively (Terraform, AWS CDK, CloudFormation) instead of manual console clicks, so environments are reproducible, reviewable, and version-controlled.

Why this matters especially for AI infra

AI infrastructure has unusually high-stakes configuration drift risk: an inference endpoint's instance type directly drives cost (GPU instances are expensive), IAM permissions around model access have real governance/compliance implications, and reproducing "the exact environment that produced this model" is essential for audit trails in regulated industries. Manual console configuration makes all of this untraceable.

My real example / how this connects to what I already do

The same discipline behind config-driven, version-controlled architecture in the sanctions screening API — treating matching thresholds and watchlist source configuration as reviewable, version-controlled artifacts rather than hardcoded or manually toggled — is exactly the instinct IaC applies to AI infrastructure: nothing about "what model is deployed, with what resources, with what access" should live only in someone's memory of what they clicked in a console.

Trade-off
CDKSame language as your application code (TypeScript/Python/C#) — lower context-switching cost for application teams also owning infra.
TerraformCloud-agnostic, huge ecosystem, often the enterprise standard already in place — the pragmatic choice when an org already has Terraform expertise and multi-cloud isn't hypothetical.
Say this in interview

"I treat AI infrastructure as needing IaC discipline even more than typical application infrastructure, because the cost and governance stakes of a wrong instance type or an overly broad IAM role are higher, and because reproducing exactly what infrastructure produced a given model version is often a genuine compliance requirement, not just good practice."

Inference Scaling & Cost

GPU-backed inference is expensive — the scaling decisions here have direct P&L impact
Real-time vs Batch vs Serverless inference
Real-time endpointsAlways-on, low-latency, but you pay for idle capacity even with zero traffic — right for user-facing interactive experiences that need consistent sub-second response.
Serverless inferenceScales to zero, pay-per-use — right for spiky, unpredictable, or low-volume traffic, at the cost of cold-start latency (the same trade-off as Lambda, covered in the AWS page).
Batch/asynchronous inferenceRight for non-interactive workloads that can tolerate delay (nightly scoring, bulk document processing) — much cheaper per-inference than real-time, since you're not paying for standing capacity between requests.
Cost levers that matter most at platform-lead scale
  • Right-sizing instance types — GPU instances vary enormously in cost; matching model size to instance size (not defaulting to the biggest available) is often the single largest cost lever.
  • Model quantization/distillation — running a smaller, optimized version of a model where full precision isn't needed, meaningfully cutting inference cost and latency.
  • Prompt caching (for LLM APIs) — Bedrock and most LLM providers support caching repeated prompt prefixes, which can substantially cut cost for RAG systems that repeat the same system prompt/context across many calls.
  • Auto-scaling on the right metric — for LLM inference specifically, request queue depth or token throughput is often a better scaling signal than raw CPU/GPU utilization.
Say this in interview

"At platform-lead level, inference cost isn't an implementation detail — it's a direct architecture decision with real P&L impact. I'd default to matching the inference pattern (real-time, batch, or serverless) to the actual traffic shape rather than always reaching for real-time endpoints, and I'd treat prompt caching and right-sized instances as standard cost hygiene, not optimizations to revisit later."

Governance & Guardrails

Where security, compliance, and AI platform architecture actually intersect

Define: The controls that ensure AI systems operate within acceptable bounds — content filtering (blocking harmful outputs), PII detection/redaction, access control over which teams can deploy or call which models, and audit logging of model inputs/outputs for compliance review.

Bedrock Guardrails as a concrete example

A managed capability to define denied topics, content filters (violence, hate speech, etc.), PII detection/masking, and word filters — applied consistently across any Bedrock-based application, rather than every team re-implementing their own ad-hoc content filtering. This is the kind of platform capability that turns "every team solves AI safety themselves" into "the platform provides it once, centrally."

Why this is a first-class platform concern, not an afterthought

This is precisely where the JD's "navigating security, governance, architecture, and business stakeholders" shows up concretely — a platform lead has to satisfy security teams (data doesn't leak, PII is handled correctly), governance/compliance teams (audit trails exist, model decisions are explainable enough for the domain), and business stakeholders (the platform is actually usable and fast to build on) simultaneously, and these pull in different directions if not deliberately balanced.

Say this in interview

"I think about AI governance as a platform capability, not a per-project bolt-on — centralizing guardrails, PII handling, and audit logging at the platform layer means every team building on it inherits compliant behavior by default, rather than each team needing security sign-off individually on their own ad-hoc implementation. That's also usually the fastest path to actually satisfying security and governance stakeholders without slowing down every individual team."

Rapid Recall Drill

Bedrock or SageMaker as the default platform choice?
Bedrock-first — fastest to production, governance built in. SageMaker specifically when you need custom training or full infra control.
What makes MLOps different from standard CI/CD?
A model can silently degrade with no code change, purely from data drift — needs monitoring and automated, metric-gated retraining, not just deployment automation.
Default vector store choice for a new RAG project?
Bedrock Knowledge Bases — managed, fastest to value; move to self-managed OpenSearch when you need chunking/hybrid-search control.
Why does AI infra need IaC especially, not just application code?
High-stakes cost (GPU instance sizing) and compliance implications (IAM scoping, reproducible training environments for audit).
Biggest inference cost lever, most often overlooked?
Right-sizing instance type to model size, plus prompt caching for repeated LLM context — often bigger levers than architecture changes.
Why treat AI governance as a platform capability, not per-project?
Centralizing guardrails/PII handling/audit logging means every team inherits compliant behavior by default, rather than re-solving security sign-off individually.
