ExecutorService & Thread Pools

Why you almost never call `new Thread()` directly in real code
ThreadPool / Task.Run ↔ ExecutorService
Question 1

Submit 5 tasks to a fixed thread pool of 2 threads, and collect all their results once complete.

▸ Show solution 
ExecutorService executor = Executors.newFixedThreadPool(2);
List<Callable<Integer>> tasks = IntStream.rangeClosed(1, 5)
    .mapToObj(i -> (Callable<Integer>) () -> i * i)
    .collect(Collectors.toList());

List<Future<Integer>> futures = executor.invokeAll(tasks);
List<Integer> results = new ArrayList<>();
for (Future<Integer> f : futures) {
    results.add(f.get());  // blocks until each is done
}
executor.shutdown();
Callable vs Runnable: Use Callable<T> when a task needs to return a value or throw a checked exception; Runnable when it doesn't. invokeAll submits all tasks and blocks until every one completes, returning Futures in the same order as submission — cleaner than manually calling .submit() in a loop when you specifically want to wait for the whole batch.
Never forget shutdown(): An ExecutorService's threads don't die on their own when tasks finish — forgetting to call .shutdown() is a classic resource leak that keeps a JVM alive indefinitely in some contexts. This is functionally the same discipline as disposing an IDisposable in .NET.
Question 2

What's the practical difference between newFixedThreadPool(n), newCachedThreadPool(), and newSingleThreadExecutor() — and which would you pick for a burst of 10,000 short-lived tasks?

▸ Show solution
newFixedThreadPool(n)Fixed number of threads, unbounded queue for excess tasks — predictable resource usage, but a burst can queue up unboundedly, growing memory if tasks arrive faster than they complete.
newCachedThreadPool()Creates new threads as needed, reuses idle ones, no real upper bound — dangerous for a 10,000-task burst since it can spawn thousands of threads and exhaust system resources.

For the 10,000 short-lived task burst: a newFixedThreadPool sized to available cores (or a custom ThreadPoolExecutor with an explicit bounded queue and rejection policy) is the safer choice — cached pool's unbounded thread creation is the classic way to accidentally take down a production service under a traffic spike.

Say this in interview: "I avoid newCachedThreadPool in production for anything with unpredictable volume, because it has no real ceiling on thread creation — a traffic spike can spawn enough threads to exhaust memory or hit OS thread limits. I'd use a fixed or custom bounded pool with an explicit rejection policy so the failure mode is a controlled backpressure signal, not an uncontrolled resource exhaustion."

CompletableFuture

Java's async/await — chaining, combining, and handling failure without blocking
async/await + Task.WhenAll ↔ CompletableFuture + thenCompose/allOf
Question 3

Fetch a user by ID asynchronously, then use that user's ID to asynchronously fetch their orders — chain these two async calls without blocking in between.

▸ Show solution 
CompletableFuture<List<Order>> ordersFuture =
    fetchUserAsync(userId)                       // CompletableFuture<User>
        .thenCompose(user -> fetchOrdersAsync(user.getId()));  // CompletableFuture<List<Order>>

List<Order> orders = ordersFuture.get();  // block only at the very end, if needed
thenCompose vs thenApply — the question that separates surface knowledge from real understanding: thenApply is for a synchronous transform (T → R). thenCompose is for when your next step itself returns a CompletableFuture (T → CompletableFuture<R>) — using thenApply here would give you the wrong type: CompletableFuture<CompletableFuture<List<Order>>>, a nested future, same shape problem as map vs flatMap on streams.
Question 4

Call three independent, unrelated async services in parallel, and combine their three results into one object once all three complete.

▸ Show solution 
CompletableFuture<String> f1 = fetchInventoryAsync(sku);
CompletableFuture<BigDecimal> f2 = fetchPriceAsync(sku);
CompletableFuture<Rating> f3 = fetchRatingAsync(sku);

CompletableFuture<ProductSummary> combined = CompletableFuture
    .allOf(f1, f2, f3)
    .thenApply(v -> new ProductSummary(f1.join(), f2.join(), f3.join()));
Why this matters architecturally: allOf lets three independent I/O calls run concurrently instead of sequentially — three 200ms calls take ~200ms total instead of ~600ms. This is the same instinct as Task.WhenAll in .NET. Calling .join() after allOf has already completed is safe (non-blocking in practice, since allOf already guaranteed completion) — calling .get()/.join() on any of them *before* allOf completes is what would actually block.
Question 5

Handle a failure in an async chain — if fetching a user fails, fall back to a default guest user instead of propagating the exception.

▸ Show solution 
CompletableFuture<User> userFuture = fetchUserAsync(userId)
    .exceptionally(ex -> {
        log.warn("User fetch failed, falling back to guest", ex);
        return User.guest();
    });
exceptionally vs handle: exceptionally only runs on failure and must return the same type T, as a recovery value. handle(BiFunction<T, Throwable, R>) runs on both success and failure, giving you a single place to branch on whether an exception occurred — useful when you want unified logic regardless of outcome, rather than a pure fallback path.

Thread Safety

synchronized, volatile, and atomic — three different tools for three different problems
Question 6

This counter is incremented from multiple threads and the final count is consistently wrong. Fix it, and explain exactly why the original was broken.

class Counter {
    private int count = 0;
    public void increment() { count++; }  // BUG
    public int get() { return count; }
}
▸ Show solution

Why it's broken: count++ is not atomic — it's actually three separate steps (read count, add 1, write count back). Two threads can both read the same value before either writes back, and one increment gets silently lost. This is a textbook race condition.

class Counter {
    private final AtomicInteger count = new AtomicInteger(0);
    public void increment() { count.incrementAndGet(); }
    public int get() { return count.get(); }
}
Why AtomicInteger over synchronized here: For a single simple counter operation, AtomicInteger uses CPU-level compare-and-swap (CAS) instructions — no thread ever blocks waiting for a lock, just retries the CAS if another thread beat it to the update. This is measurably faster under contention than acquiring a full synchronized lock for something this simple. Reach for synchronized when you need to protect a multi-step operation across several variables atomically together — Atomic classes only protect a single variable.
Question 7

What does volatile actually guarantee, and what does it explicitly NOT guarantee? Give an example of a bug caused by assuming volatile provides more than it does.

▸ Show solution

What volatile guarantees: Visibility — a write to a volatile variable by one thread is immediately visible to all other threads reading it (prevents threads from working off a stale, cached local copy of the value). It also establishes a happens-before ordering for that variable.

What it does NOT guarantee: Atomicity of compound operations. volatile int count; count++; is still a race condition — volatile makes the read and the write each individually visible correctly, but doesn't make the read-modify-write sequence atomic as a whole. This is the single most common volatile misconception.

Say this in interview: "I think of volatile as solving visibility, not atomicity — it's the right tool for a simple flag one thread sets and another polls, like a 'shouldStop' boolean. The moment the operation is a compound read-modify-write, like incrementing a counter, volatile alone doesn't make it thread-safe — that needs Atomic classes or synchronized."

Deadlock

The classic two-lock scenario — recognize it, then fix it
Question 8

Two threads, two locks — this code can deadlock. Explain exactly how, then fix it.

// Thread A calls transfer(accountX, accountY, 100)
// Thread B calls transfer(accountY, accountX, 50)  — at the same time
void transfer(Account from, Account to, int amount) {
    synchronized (from) {
        synchronized (to) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
▸ Show solution

How the deadlock happens: Thread A locks accountX, then tries to lock accountY. Simultaneously, Thread B locks accountY, then tries to lock accountX. Each thread now holds the lock the other one needs, and neither will ever release — a classic circular wait, one of the four necessary conditions for deadlock (mutual exclusion, hold-and-wait, no preemption, circular wait).

void transfer(Account from, Account to, int amount) {
    Account first = from.getId() < to.getId() ? from : to;
    Account second = from.getId() < to.getId() ? to : from;
    synchronized (first) {
        synchronized (second) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
The fix — lock ordering: Always acquire locks in a consistent, globally-agreed order (here, by account ID) regardless of which account is "from" and which is "to." If every thread always locks the lower ID first, circular wait becomes structurally impossible — there's no scenario where two threads are each waiting on a lock the other holds, because both always try to acquire the smaller ID first.

Producer-Consumer

The pattern behind message queues, thread pools, and half the concurrency interview questions ever asked
Question 9

Implement a producer thread adding items to a shared bounded buffer, and a consumer thread removing them — without busy-waiting.

▸ Show solution 
BlockingQueue<Integer> buffer = new ArrayBlockingQueue<>(10);

// Producer thread
new Thread(() -> {
    for (int i = 0; i < 100; i++) {
        try {
            buffer.put(i);  // blocks automatically if buffer is full
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}).start();

// Consumer thread
new Thread(() -> {
    while (true) {
        try {
            int item = buffer.take();  // blocks automatically if buffer is empty
            process(item);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            break;
        }
    }
}).start();
Why BlockingQueue, not a manually-coded wait/notify implementation: The classic textbook answer to this question hand-rolls synchronization with wait()/notify() and a manually managed buffer — technically correct, but BlockingQueue implementations (ArrayBlockingQueue, LinkedBlockingQueue) already solve exactly this problem, correctly, with none of the subtle bugs (missed notifications, spurious wakeups) that hand-rolled wait/notify code is notorious for. A senior answer knows the manual mechanics exist but reaches for the battle-tested primitive in real code — same instinct as not hand-rolling your own thread pool when ExecutorService exists.
The interrupt handling detail people miss: Catching InterruptedException and just swallowing it is a common, subtly wrong pattern — it clears the thread's interrupted status, meaning any calling code checking for interruption will incorrectly think none occurred. Re-calling Thread.currentThread().interrupt() restores that status for callers further up the stack to observe.

Advanced Scenarios

The ones that come up specifically at senior/lead level
Question 10

Implement a thread-safe lazy-initialized singleton, and explain why the naive version is broken.

▸ Show solution 
class Singleton {
    private static volatile Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                    // 1st check, no lock — fast path
            synchronized (Singleton.class) {
                if (instance == null) {             // 2nd check, inside lock
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
Why the naive "just synchronize the whole method" version is worse, not just simpler: Synchronizing the entire getInstance() method forces every single call, forever, to acquire a lock — even long after the singleton is already created and no synchronization is needed at all. This double-checked locking pattern only pays the lock cost on the rare first-initialization race, then takes a fast unsynchronized path for every call after that.
Why volatile is mandatory here, not optional: Without volatile, another thread could see a partially-constructed object due to instruction reordering — the reference gets assigned before the constructor has fully finished running, a genuinely subtle JVM memory model issue. This is exactly the kind of detail that separates "recited double-checked locking" from actually understanding why each piece is there.
Question 11

You have a shared HashMap being read by many threads and occasionally written by one. What are your options, ranked by how you'd actually choose?

▸ Show solution
ConcurrentHashMap (usual first choice)Lock-striped internally — different segments of the map can be written concurrently without one global lock, and reads generally don't block at all. The right default for most shared-map scenarios.
Collections.synchronizedMap(new HashMap<>())Wraps every single operation in one global lock — simple, but effectively single-threaded for writes and even reads block each other, unlike ConcurrentHashMap's finer-grained locking.

For "many reads, rare writes" specifically: if writes are truly rare and reads vastly dominate, ConcurrentHashMap is still the right default — its read path is essentially lock-free in the common case, which is exactly the profile described.

Say this in interview: "I reach for ConcurrentHashMap by default for any shared map under concurrent access — it's specifically designed for exactly this read-heavy, occasional-write pattern, with much finer-grained locking than wrapping a HashMap in a single synchronized block."

Common Gotchas — Rapid Fire

Difference between .get() with a timeout and .join() on a CompletableFuture?
get() throws checked exceptions (ExecutionException, InterruptedException) and accepts a timeout; join() throws unchecked CompletionException and has no built-in timeout — join() is more convenient inside lambda chains where checked exceptions are awkward.
What's a spurious wakeup, and why do you always check the condition in a while loop, not an if, after wait()?
A thread can wake from wait() without actually being notified (a JVM-level artifact) — using while (!condition) { wait(); } instead of if re-checks the condition after waking, protecting against acting on a false wakeup.
Does calling Thread.stop() ever belong in real code?
No — deprecated and inherently unsafe, since it can release locks mid-operation leaving shared state corrupted. Use a volatile flag the thread checks itself, or interrupt() combined with cooperative cancellation instead.
Is ArrayList thread-safe for concurrent reads while one thread writes?
No — needs CopyOnWriteArrayList (great for read-heavy, rarely-written lists, since reads never block) or explicit synchronization/Collections.synchronizedList otherwise.
