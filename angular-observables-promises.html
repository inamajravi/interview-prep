Observables vs Promises

Not an interview reference — this is the "make it actually click" page. If RxJS has felt confusing, it's usually because Observables get explained as "like Promises but different" instead of explaining the one core idea that makes everything else make sense.

The One Idea That Unlocks Everything Else

Read this section slowly — everything else on this page is just this idea applied

A Promise represents ONE value that will arrive ONCE, in the future. You ask for something, you wait, you get exactly one answer (or exactly one error), and then it's done forever. Think of ordering a pizza — you place one order, you wait, one pizza arrives, transaction complete.

An Observable represents a STREAM of values that can arrive ZERO, ONE, OR MANY times, over time. Think of subscribing to a YouTube channel — you don't get "one video" and then the subscription is done. You get however many videos that channel uploads, whenever they upload them, for as long as you stay subscribed. You could also unsubscribe at any point and stop receiving anything further.

That's it. That's the whole conceptual difference. Promise = one event in the future. Observable = an ongoing subscription to a stream of events, which might be zero events, one event, or an endless sequence of events, and which you can cancel at any time. Every other difference between them (cancellation, operators, the `subscribe` method, "cold" vs "hot") is a direct consequence of this one idea, not a separate thing to memorize.
Say this in interview

"A Promise resolves once, with one value. An Observable is a subscription to a stream that can emit any number of values over time — that's the core distinction everything else, like cancellation and operators, follows from."

What a Promise Actually Is

You already know this — it's the same shape as .NET's Task
.NET: Task<T> / async-await ↔ JavaScript: Promise<T> / async-await

A JavaScript Promise is functionally identical to a .NET Task<T> — an object representing "a value that isn't ready yet, but will be." You call an async function, get a Promise back immediately, and either .then() onto it or await it, exactly like awaiting a Task in C#.

// Fetch a user, once. One value, one time.
fetch('/api/user/42')
    .then(response => response.json())
    .then(user => console.log(user));

// or with async/await — feels exactly like C#
async function loadUser() {
    const response = await fetch('/api/user/42');
    const user = await response.json();
    console.log(user);
}
The key limitation to notice: once you call fetch(...), that HTTP request is already happening. There is no built-in way to cancel it. If you no longer care about the result (say, the user navigated away from the page), the Promise doesn't know or care — it'll still resolve eventually, and any .then() callback attached to it will still run, whether you still want that or not.
Say this in interview

"A Promise is the direct JavaScript equivalent of a .NET Task — same async/await ergonomics, same 'one value, eventually' contract. The thing I'd flag as a real limitation is that a Promise can't be cancelled once started — that's actually the main reason Angular defaults to Observables for things like HTTP calls."

What an Observable Actually Is

Not a fancier Promise — a genuinely different shape of thing

An Observable is, underneath everything, just a function that Angular/RxJS calls for you when someone subscribes — and that function can call back with a value (next) as many times as it wants, whenever it wants, until it either finishes (complete) or fails (error).

const myObservable = new Observable(subscriber => {
    subscriber.next('first value');
    subscriber.next('second value');
    setTimeout(() => {
        subscriber.next('a value that arrived later');
        subscriber.complete();  // no more values coming after this
    }, 1000);
});

myObservable.subscribe(value => console.log(value));
// Logs: 'first value', 'second value'
// ...one second later, logs: 'a value that arrived later'
Notice something important: nothing happened at all until .subscribe() was called. Creating an Observable doesn't run anything — it's just a description of "here's what will happen when someone actually subscribes." This is called being lazy (or "cold"), and it's a real behavioral difference from Promises, which start running the instant they're created, whether anyone is listening for the result or not.
Say this in interview

"An Observable is lazy — nothing executes until subscribe() is called. A Promise is eager — it starts running the moment it's created, subscribed to or not. That laziness is exactly what makes Observables cancellable: if no one's subscribed yet, or you unsubscribe, the underlying work can simply never happen or get torn down."

subscribe() — What Actually Happens

This is the part that trips people up most — think of it as "pressing play," not "getting a result"

Calling .subscribe(callback) doesn't "get the value" the way await does with a Promise. It says: "start running this Observable's logic now, and every time it produces a value, call my callback with it." That's why it's the correct mental model to think of an Observable as something you press play on, not something you retrieve a value from.

In an Angular HTTP call specifically: calling http.get('/api/users') alone does nothing — no network request is sent yet. It only fires when something calls .subscribe() on it (or the async pipe does that for you in a template, covered further down). This surprises a lot of people coming from Promise-based fetch, where the request starts the instant you call the function. 
const users$ = this.http.get('/api/users');  // nothing happens yet — no request sent

users$.subscribe(users => {                   // THIS is what actually fires the HTTP call
    console.log(users);
});
Say this in interview

"I think of subscribe() as pressing play on the Observable's underlying logic, not retrieving a value that's already in flight. For an HTTP Observable specifically, that means the actual network request doesn't fire until something subscribes — a common surprise for anyone used to fetch() or a Promise-based HTTP client, where the call is already happening the moment you invoke it."

Cancellation — the Real Superpower

The single biggest practical reason Angular defaults to Observables over Promises

Because subscribing is what starts the work, unsubscribing can stop it — genuinely, not just "ignore the result." If an HTTP request is still in flight and you unsubscribe, Angular's HttpClient actually aborts the underlying request. A Promise offers you no equivalent — once started, it runs to completion no matter what, and you're just choosing whether to listen to the result or not.

Where this matters in real Angular code: a user types in a search box, firing an HTTP request per keystroke. Without cancellation, five keystrokes means five HTTP requests all racing to complete, and whichever slow one finishes last "wins" and overwrites the display — even if it's answering an old, outdated query. With Observables, the switchMap operator automatically unsubscribes from (and cancels) the previous request the moment a new keystroke fires — this is exactly the pattern from the main Angular reference page's RxJS section, and now you know why switchMap needs Observables specifically to do this: Promises simply have no cancellation mechanism to hook into.
Say this in interview

"Cancellation is the practical reason I reach for Observables over Promises for HTTP calls specifically — a stale, in-flight request can be genuinely aborted on unsubscribe, which is exactly what switchMap relies on for a typeahead search. A Promise-based fetch has no equivalent; you can only ignore its result once it resolves, not stop it from happening."

Streams of Values Over Time

The scenario a Promise literally cannot represent, no matter how you contort it

Some things aren't "one value in the future" — they're an ongoing sequence: every mouse click, every keystroke, every WebSocket message, every tick of a timer. A Promise has no way to model this at all — it resolves once, then it's done. An Observable models it directly and naturally, because "emit a value, possibly many times, over time" is exactly what it's built for.

// Every click, for as long as this subscription lives — not just the first one
fromEvent(document, 'click').subscribe(event => {
    console.log('Clicked at', event.clientX, event.clientY);
});

// A live countdown timer emitting a new value every second, forever
interval(1000).subscribe(seconds => console.log(`${seconds}s elapsed`));
This is the reframe that usually makes Observables finally click: don't think "how is this different from a Promise" — think "this represents an ongoing stream of things happening, and a Promise was never trying to solve that problem in the first place." An HTTP call happens to only emit one value (the response) and then completes — which is why it can look Promise-like at first — but it's using the same general-purpose "stream" machinery as a WebSocket connection or a mouse-click listener, not a special case bolted on separately.
Say this in interview

"HTTP calls in Angular use Observables not because a single response particularly needs stream semantics, but for consistency — the same Observable machinery used for HTTP also naturally handles WebSocket messages, user input events, and timers, which genuinely can't be modeled as a single Promise resolution. It's one consistent async model instead of a different tool per scenario."

The Async Pipe — Angular's Built-In Answer to "Don't Forget to Unsubscribe"

The single most important practical pattern for a beginner to adopt immediately

Every manual .subscribe() call in a component creates an ongoing subscription that must be manually cleaned up (usually in ngOnDestroy) or it leaks — the subscription keeps listening even after the component is gone. The async pipe, used directly in a template, subscribes automatically when the component initializes and unsubscribes automatically when the component is destroyed — no manual cleanup code needed at all.

Manual subscribe (needs cleanup) 
// component.ts
users: User[] = [];
private sub: Subscription;

ngOnInit() {
  this.sub = this.userService.getUsers()
    .subscribe(users => this.users = users);
}

ngOnDestroy() {
  this.sub.unsubscribe();  // easy to forget!
}
Async pipe (self-managing) 
// component.ts
users$ = this.userService.getUsers();

// template.html
<div *ngFor="let user of users$ | async">
  {{ user.name }}
</div>
// subscribes on init, unsubscribes
// automatically on destroy — nothing
// else to write
Say this in interview

"My default is the async pipe over manual subscribe wherever the value is only needed in the template — it removes an entire category of memory-leak bugs from forgetting to unsubscribe, since Angular manages the subscription lifecycle for you. I'd only reach for a manual subscribe when I genuinely need the value inside component logic, not just for display."

Subject & BehaviorSubject, Simply

The two you'll actually use constantly — explained without jargon first

A plain Subject is both an Observable AND something you can manually push values into from the outside — think of it as a live radio broadcast: if you tune in (subscribe) after something was already announced, you missed it. You only get whatever's broadcast after you start listening.

A BehaviorSubject is the same idea, but it always remembers and immediately replays its most recent value to any new subscriber — think of it as a radio broadcast with a "currently playing" display: even if you tune in late, you instantly see what's playing right now, not just future updates.

const subject = new Subject<number>();
subject.next(1);
subject.subscribe(val => console.log('A:', val));  // A subscribes AFTER 1 was sent — misses it
subject.next(2);  // A logs: 'A: 2'

const behaviorSubject = new BehaviorSubject<number>(0);  // needs an initial value
behaviorSubject.next(1);
behaviorSubject.subscribe(val => console.log('B:', val));  // B logs: 'B: 1' IMMEDIATELY, even though it subscribed late
behaviorSubject.next(2);  // B logs: 'B: 2'
Why this matters practically: BehaviorSubject is the standard building block for shared application state in Angular services (covered on the main Angular reference page's State Management section) precisely because of this "always has a current value" property — a component that subscribes to shared state late (after the app already started) still immediately gets the current state, not nothing.
Say this in interview

"The practical difference is whether a late subscriber gets the current value immediately or has to wait for the next update — BehaviorSubject always has a 'current value' ready to hand to any new subscriber instantly, which is exactly why it's the standard choice for shared state services, where a component mounting late still needs to see what the state currently is."

Converting Between Them

You'll need this occasionally — a third-party library that only speaks Promises
// Observable -> Promise (grab just the next single value)
import { firstValueFrom } from 'rxjs';

const user = await firstValueFrom(this.http.get('/api/user/42'));

// Promise -> Observable
import { from } from 'rxjs';

const users$ = from(fetch('/api/users').then(r => r.json()));
Worth knowing: converting an Observable to a Promise via firstValueFrom throws away everything that makes Observables useful — cancellation, multiple values over time — collapsing it down to "just give me the next single value, once." That's sometimes exactly what you want (a one-off HTTP call inside an async function), but it's a deliberate downgrade, not a free conversion.
Say this in interview

"Converting Observable to Promise with firstValueFrom is a real trade-off, not just syntax — you're deliberately giving up cancellation and multi-value support to get simpler async/await ergonomics for a one-off case. I wouldn't reach for it as a default just because await feels more familiar than subscribe."

Quick Self-Check

If these all make sense without re-reading, the concept has clicked
In one sentence, what's the core difference between a Promise and an Observable?
A Promise is one value, once. An Observable is a subscription to a stream that can emit zero, one, or many values over time, and can be cancelled.
Does calling http.get(...) send a network request immediately?
No — nothing happens until something calls .subscribe() on it (or the async pipe does that for you).
Why can't you cancel a Promise-based fetch call?
A Promise starts running the instant it's created — there's no subscription to cancel, only a result you can choose to ignore once it resolves.
Why does switchMap need Observables, not Promises, to cancel a stale HTTP request?
Cancellation on an Observable works via unsubscribing, which actually aborts the in-flight work — Promises have no equivalent hook to cancel anything already started.
Why use the async pipe instead of manually calling .subscribe() in a component?
It automatically subscribes on init and unsubscribes on destroy — removes the entire class of bugs caused by forgetting manual cleanup.
A component subscribes to shared state after the app already started — Subject or BehaviorSubject?
BehaviorSubject — it immediately replays its current value to a late subscriber; a plain Subject would give that subscriber nothing until the next new value.
