EKS Architecture

What "managed" actually means — and what you still own

Define: EKS is AWS's managed Kubernetes control plane — AWS runs and patches the API server, etcd, and scheduler across multiple Availability Zones for you. You bring the worker nodes (or use Fargate to skip that too) and everything you deploy onto the cluster.

Analogy: Same analogy as the Kubernetes page's AKS entry, but worth restating precisely for EKS: it's booking a flight rather than building an airline — AWS handles the runway, air traffic control, and safety inspections (the control plane); you still own what's in your cargo hold and how it's packed (your workloads, node configuration, and IAM).
What AWS owns vs what you still own
AWS ownsControl plane availability/patching, etcd backups and encryption, API server scaling, Kubernetes version upgrades (you trigger them, AWS executes the mechanics).
You still ownWorker node patching (unless using Fargate or Bottlerocket with managed updates), IAM policy design, networking/VPC configuration, add-on version management, and everything about what you actually deploy.
Why this distinction matters in an interview

"Managed Kubernetes" is a common phrase candidates use loosely — being precise about exactly which layer is managed (control plane) versus which layer still requires real operational ownership (nodes, networking, IAM, add-ons) is what signals actual EKS experience versus a surface-level read of the marketing page.

Say this in interview

"EKS removes control plane operations specifically — etcd, API server availability, version patching of that layer — but node management, networking, and IAM integration are still real architectural decisions I own. I wouldn't describe EKS as 'fully managed Kubernetes' without that distinction, because the node and networking layer is where most of the actual platform engineering work happens."

Node Options — Managed Node Groups, Self-Managed, Fargate

Three ways to actually run your Pods, with real operational trade-offs between them
Managed Node Groups (MNG)AWS provisions and manages the EC2 instances as an Auto Scaling Group, handles node draining during updates, and simplifies the AMI/upgrade lifecycle. The default, sensible choice for most workloads — meaningfully less operational overhead than self-managed nodes.
Self-Managed Node GroupsYou provision and manage the EC2 instances/ASG yourself, full control over AMI, bootstrap scripts, and instance lifecycle. Needed when you require a custom AMI, unusual instance configuration, or specific bootstrap behavior MNG doesn't support.
Fargate for EKSNo nodes to manage at all — each Pod runs in its own isolated compute environment, sized automatically to the Pod's resource requests. Genuinely serverless Kubernetes: no node patching, no capacity planning, pay per Pod's actual resource usage.
Why Fargate isn't the default for everything
Real Fargate limitationsNo DaemonSets (a common pattern for node-level agents like log shippers), no privileged containers, no GPU workloads, and higher per-Pod cost at sustained high density compared to bin-packing many Pods onto shared EC2 nodes. It's the right default for bursty, security-isolated, or operationally-simple workloads — not a universal replacement for node groups.
Say this in interview

"I default to Managed Node Groups for most workloads — best balance of operational simplicity and flexibility. I'd reach for Fargate specifically for workloads that benefit from per-Pod isolation and don't need DaemonSets or GPU access, and self-managed nodes only when there's a genuine requirement MNG can't satisfy, like a custom AMI or non-standard bootstrap process."

Networking — the VPC CNI

The single most distinctive, and most commonly misunderstood, piece of EKS networking

Define: By default, EKS uses the Amazon VPC CNI plugin, which gives every Pod a real, routable IP address directly from your VPC's subnet — unlike most other Kubernetes networking implementations (Calico, Flannel) which use an overlay network with a separate, non-VPC-routable IP space for Pods.

Analogy: An overlay network (the non-AWS-default approach) is like giving every apartment in a building an internal-only extension number that only works within the building's own phone system — someone outside has to go through a receptionist (NAT/gateway) to reach them. The VPC CNI instead gives every apartment its own real street address, directly reachable and routable by anyone on the same network, with no translation layer in between.
Why this design, and the real trade-off it creates

Giving Pods real VPC IPs means they can be reached directly by other AWS services (and reach them) using standard VPC networking, security groups, and routing — no overlay translation overhead, simpler troubleshooting, and native integration with VPC-level tools. The real cost: IP address exhaustion. Each EC2 instance type has a hard limit on how many ENI (network interface) IP addresses it can attach, which directly caps how many Pods can run per node — a genuinely common production issue on smaller instance types running many small Pods.

Trade-off / the actual EKS-specific mitigation
Prefix Delegation modeA VPC CNI feature that assigns IP address prefixes (not just individual IPs) to ENIs, dramatically increasing the Pod-per-node density ceiling — the standard fix once you hit IP exhaustion on smaller instance types.
Security Groups for PodsA related VPC CNI capability letting you attach a specific EC2 security group directly to individual Pods (not just the node) — meaningfully finer-grained network policy than Kubernetes NetworkPolicy alone provides, at the cost of added configuration complexity.
Say this in interview

"The VPC CNI giving every Pod a real routable VPC IP is the single most distinctive thing about EKS networking versus vanilla Kubernetes — it simplifies integration with other AWS services but creates a real IP exhaustion risk tied directly to instance type ENI limits. I'd flag Prefix Delegation mode as the standard fix once that becomes a constraint, rather than just reaching for bigger instances by default."

IAM Integration — IRSA

The EKS-specific concept most likely to come up, and most likely to separate real experience from surface knowledge

Define: IRSA — IAM Roles for Service Accounts — lets you attach a specific, scoped IAM role directly to a Kubernetes Service Account, so Pods using that Service Account can call AWS APIs (S3, DynamoDB, SQS, etc.) with exactly the permissions that role grants — no shared credentials, no overly broad node-level IAM role covering every Pod on that node.

Analogy: Without IRSA, every Pod on a node effectively inherits the node's own IAM role — like every apartment in a building sharing one master key that opens every door in the city the building manager has access to. IRSA gives each apartment its own key, cut to open only the specific doors that apartment actually needs — even though they're all in the same building.
Why it exists — the problem before IRSA

Before IRSA, the common (and risky) pattern was granting the EC2 node's IAM role broad enough permissions to cover every Pod that might run on it — meaning a compromised or misconfigured Pod could access AWS resources far beyond what it actually needed, since it inherited the node's entire permission set. IRSA lets you follow the principle of least privilege at the Pod level, not just the node level — directly connecting back to the Zero Trust and least-privilege concepts covered in the Security page.

How it actually works, at the level worth knowing

IRSA uses an OIDC identity provider associated with the EKS cluster — the Service Account gets a Kubernetes-issued, short-lived token that AWS's STS (Security Token Service) trusts and exchanges for temporary AWS credentials scoped to the linked IAM role, via AssumeRoleWithWebIdentity. No long-lived AWS credentials are ever stored in the cluster — the whole flow is short-lived token exchange, which also directly satisfies the "no static secrets, rotate constantly" instinct from good security practice generally.

Trade-off
Always use IRSA whenA Pod needs to call any AWS API — this should be the default pattern for essentially every workload, not an advanced/optional feature.
The anti-pattern to flagBroad node-instance-role permissions that every Pod on that node inherits — this is exactly the kind of over-privileged default an interviewer wants to hear you identify and correct, given how directly it maps to the Broken Access Control and least-privilege themes in the Security page.
Say this in interview

"IRSA is how I'd apply least-privilege at the Pod level on EKS specifically — scoping IAM permissions to exactly what a given Service Account's Pods need, rather than letting every Pod on a node inherit a broad shared node-level role. It's the direct EKS-specific expression of the same zero-trust, least-privilege discipline I'd apply anywhere else — no Pod should have more AWS access than its own specific job requires."

Load Balancing & Ingress — the AWS Load Balancer Controller

How the Kubernetes Service/Ingress concepts you already know map onto real AWS load balancers
Kubernetes: Service type=LoadBalancer / Ingress ↔ AWS: Network Load Balancer / Application Load Balancer

Define: The AWS Load Balancer Controller is what actually watches for Kubernetes Service and Ingress objects on EKS and provisions real AWS load balancers to match — a Service of type: LoadBalancer provisions a real NLB, and an Ingress object provisions a real ALB, directly connecting back to the ALB-vs-NLB decision already covered on the AWS page (Layer 7 content-aware routing vs Layer 4 raw throughput).

Two ALB target modes — a real EKS-specific decision
Instance modeTraffic routes to a NodePort on each EC2 instance, then gets forwarded internally to the right Pod via kube-proxy — an extra network hop, but works with any CNI.
IP mode (the common EKS default with VPC CNI)The ALB routes traffic directly to each Pod's own VPC IP address, skipping the node/kube-proxy hop entirely — lower latency, and only possible because the VPC CNI already gives every Pod a real routable VPC IP in the first place. This is a direct example of the networking section above enabling a real, concrete benefit elsewhere in the stack.
Say this in interview

"The AWS Load Balancer Controller is the bridge between Kubernetes' native Service/Ingress abstractions and real AWS load balancers — and I'd specifically call out IP target mode as a concrete payoff of the VPC CNI's Pod-level VPC IPs, since it lets the ALB route straight to a Pod without an extra kube-proxy hop, which instance mode can't avoid."

Storage — CSI Drivers

Connecting Kubernetes' storage abstractions to real AWS storage services
Amazon EBS CSI DriverProvisions real EBS volumes as Kubernetes PersistentVolumes — the standard choice for a single Pod needing durable block storage (a database, for example). EBS volumes attach to exactly one node at a time — an important constraint tying directly back to the StatefulSet concept from the Kubernetes page: a Pod with EBS-backed storage that gets rescheduled to a different node requires the volume to detach and reattach.
Amazon EFS CSI DriverProvisions EFS (a network file system) — right when multiple Pods across multiple nodes need to read/write the same shared storage simultaneously, something EBS's single-node-attach model can't do at all.
Say this in interview

"The choice comes down to one question: does exactly one Pod need durable storage, or do multiple Pods need to share the same storage concurrently? EBS CSI for the first case, EFS CSI for the second — and EBS's single-node-attach constraint is exactly why a StatefulSet's stable Pod identity matters, since Kubernetes needs to know which specific Pod a given volume belongs to when rescheduling happens."

Autoscaling — Cluster Autoscaler vs Karpenter

Scaling the nodes themselves, not just the Pods — HPA from the Kubernetes page handles Pod-level scaling; this is one layer down
Cluster Autoscaler (the original approach)Watches for unschedulable Pods (no node has enough capacity) and scales an existing Auto Scaling Group to add nodes — works within the constraint of pre-defined ASG instance types and launch templates.
Karpenter (the newer, increasingly preferred approach)Provisions nodes directly, choosing the actual best-fit instance type and size for the specific pending Pods' requirements at that moment — not limited to a pre-defined ASG's fixed instance type, and generally faster to provision and more cost-efficient through better bin-packing.
Why this distinction is worth knowing precisely

Karpenter's group-less, just-in-time provisioning model is a meaningfully different architecture from Cluster Autoscaler's "scale a predefined group" model — it's increasingly the recommended default for new EKS clusters specifically because of better cost efficiency (right-sized instances, not just more of a fixed type) and faster node provisioning during scale-up events.

Say this in interview

"I'd lean toward Karpenter for new clusters — its just-in-time, right-sized provisioning tends to beat Cluster Autoscaler's fixed-ASG model on both cost and scale-up latency. Cluster Autoscaler still makes sense where an org already has mature, fixed ASG-based capacity planning and doesn't want to introduce a new provisioning model — but I wouldn't default to it for a greenfield EKS setup today."

EKS vs ECS vs Self-Managed Kubernetes

The platform-level decision underneath everything else on this page
EKSFull Kubernetes API and ecosystem — right when you need Kubernetes-native tooling, multi-cloud portability is a real (not hypothetical) requirement, or the org already has Kubernetes expertise and tooling investment.
ECS (Elastic Container Service)AWS's own simpler, proprietary container orchestrator — less operational complexity than EKS, no Kubernetes concepts to learn, tighter native AWS integration by default. Right when a team is fully committed to AWS and doesn't need Kubernetes' portability or ecosystem, and wants to minimize orchestration complexity.
Self-managed Kubernetes on EC2Full control over every layer, including the control plane — right only when there's a genuine, specific reason EKS's managed control plane doesn't satisfy (rare in practice) — the operational burden is substantial and rarely justified today given how mature EKS has become.
Say this in interview

"I don't treat Kubernetes as automatically the right default — if a team is fully AWS-native with no multi-cloud requirement and wants to minimize orchestration complexity, ECS is a legitimate, often under-considered choice. I'd reach for EKS specifically when Kubernetes' ecosystem, portability, or existing team expertise is a real driver, not just because it's the more commonly discussed option."

Rapid Recall Drill

What does EKS actually manage, precisely?
The control plane — API server, etcd, scheduler — across multiple AZs. Nodes, networking, IAM, and add-ons are still your responsibility (unless also on Fargate).
Why can Fargate not run a DaemonSet?
Each Fargate Pod runs in its own isolated compute environment with no shared node for a DaemonSet to run once-per-node on — there's no persistent node to attach to.
Why does the VPC CNI cause IP exhaustion issues that overlay-network CNIs don't?
Every Pod gets a real VPC IP from the ENI's attached IP pool, which is capped per instance type — Prefix Delegation mode is the standard fix once you hit that ceiling.
What problem does IRSA solve that a node instance role doesn't?
Scoping AWS permissions to the specific Service Account/Pod that needs them, instead of every Pod on a node inheriting one broad shared node-level IAM role.
Why does ALB IP target mode need the VPC CNI specifically?
It routes traffic directly to a Pod's own VPC IP, skipping the node/kube-proxy hop — only possible because the VPC CNI gives Pods real routable VPC IPs in the first place.
EBS or EFS for 10 Pods across 5 nodes needing the same shared files?
EFS — EBS volumes attach to exactly one node at a time and can't be shared concurrently across nodes.
Karpenter's key architectural difference from Cluster Autoscaler?
Just-in-time, right-sized node provisioning directly for pending Pods, rather than scaling a pre-defined, fixed-instance-type Auto Scaling Group.
When would you pick ECS over EKS?
Fully AWS-native team with no multi-cloud requirement, wanting to minimize orchestration complexity — Kubernetes' ecosystem/portability isn't a real driver for them.
