AKS Architecture — Free vs Standard Tier

Same "managed control plane" idea as EKS — but AKS has a pricing/SLA fork EKS doesn't
AWS: EKS control plane (always paid, ~$0.10/hr) ↔ Azure: AKS Free tier vs Standard tier

Define: Like EKS, AKS gives you a managed control plane — Azure runs the API server, etcd, and scheduler. The real difference from EKS: AKS historically offered the control plane at no extra charge on the Free tier, with the Standard tier (a real cost, comparable to EKS's control plane fee) adding a financially-backed SLA and better support for larger, production-critical clusters.

Why this fork exists, and the trade-off
Free tierNo SLA guarantee on the control plane, and a lower recommended node/Pod ceiling — fine for dev/test clusters, not recommended for production workloads with real uptime requirements.
Standard tierFinancially-backed uptime SLA, higher scale limits, and better control plane resource allocation for larger clusters — the tier you'd actually choose for anything production-facing, functionally equivalent in intent to EKS always being a paid, SLA-backed control plane.
Say this in interview

"EKS's control plane is a flat paid, SLA-backed service by default — AKS instead makes you explicitly opt into that same guarantee via the Standard tier. I'd always specify Standard tier for a production cluster discussion, the same way I'd never suggest running a production EKS workload on anything but the standard managed control plane."

Node Pools & Virtual Nodes

AKS's node model maps closely to EKS's, with one extra concept: the mandatory system pool
AWS: Managed Node Groups / Fargate ↔ Azure: Node Pools (System/User) / Virtual Nodes (ACI)
System Node Pool (AKS-specific, no direct EKS equivalent)AKS requires at least one dedicated system node pool to run critical cluster add-ons (CoreDNS, metrics-server, etc.) — best practice is keeping application workloads off it entirely, isolating them to separate User node pools. EKS has no equivalent mandatory split; its system components typically run alongside application Pods on the same managed nodes.
User Node PoolsDirectly equivalent to EKS Managed Node Groups — where your actual application workloads run, scalable and configurable per pool (different instance types, spot vs on-demand, per workload).
Virtual Nodes (backed by Azure Container Instances)AKS's equivalent to EKS Fargate — Pods run in isolated compute without a provisioned VM node, burstable and fast to scale. Similarly can't run DaemonSets, same fundamental constraint as Fargate for the same underlying reason: no persistent per-node presence to attach to.
Say this in interview

"The direct EKS parallel is User Node Pools to Managed Node Groups, and Virtual Nodes to Fargate — same trade-offs, same DaemonSet limitation on the serverless option. The one genuinely AKS-specific concept is the mandatory system node pool — I'd always isolate application workloads onto separate user pools, since starving the system pool of resources can destabilize cluster-critical add-ons in a way that has no direct EKS parallel."

Networking — Azure CNI vs Kubenet

The exact same VPC-IP-exhaustion story as EKS's VPC CNI — with an extra fork AWS doesn't have
AWS: VPC CNI (the only real default option) ↔ Azure: Azure CNI vs Kubenet (a real choice AKS makes you face upfront)
Azure CNIEvery Pod gets a real, routable IP directly from the Azure Virtual Network — exactly the same model, and exactly the same IP-exhaustion risk profile, as EKS's default VPC CNI. Needed when Pods must be directly reachable from other Azure VNet resources.
Kubenet (Azure-specific, no EKS equivalent)Pods get IPs from a separate, non-VNet-routable overlay network — nodes get real VNet IPs, but Pods don't, avoiding VNet IP exhaustion entirely at the cost of an extra NAT hop for Pod-to-VNet-resource traffic, and generally reduced feature support for newer AKS capabilities. This choice doesn't really exist on EKS, since VPC CNI is the standard default there.
Why AKS gives you this choice and EKS effectively doesn't

Kubenet exists specifically because IP exhaustion is a real, common pain point in Azure Virtual Networks with limited address space — Azure decided to offer an escape hatch (accept an overlay network's NAT overhead to sidestep VNet IP planning entirely), where AWS instead invested in VPC CNI mitigations like Prefix Delegation to solve the same underlying problem while keeping every Pod's IP real and routable.

Say this in interview

"Azure CNI is the direct parallel to EKS's VPC CNI, including the same IP exhaustion risk on a poorly-planned VNet — Kubenet is Azure's alternative path around that problem, trading real Pod-level VNet routability for avoiding IP planning altogether, which isn't really a choice EKS offers since AWS instead solved the exhaustion problem directly via Prefix Delegation. I'd default to Azure CNI for anything needing real VNet integration and reserve Kubenet for cases where VNet address space is genuinely constrained and Pods don't need direct VNet-level reachability."

Identity — AKS Workload Identity

The exact same problem IRSA solves on EKS, solved almost identically
AWS: IRSA (IAM Roles for Service Accounts) ↔ Azure: AKS Workload Identity (formerly Azure AD Pod Identity)

Define: Workload Identity lets you federate a Kubernetes Service Account with an Azure AD (Entra ID) application identity, so Pods using that Service Account can call Azure APIs (Storage, Key Vault, etc.) with exactly the permissions granted to that identity — no shared node-level credentials, no long-lived secrets stored in the cluster.

The mechanism — nearly a 1:1 match with IRSA

Just like IRSA, Workload Identity uses an OIDC federation between the AKS cluster and Azure AD — a Kubernetes-issued, short-lived token gets exchanged for a temporary Azure AD access token scoped to the linked identity, via workload identity federation. No static credentials are ever stored in the cluster, satisfying the same short-lived-credential, least-privilege discipline as IRSA and the same Zero Trust principle covered on the Security page.

A note on naming history — worth knowing if it comes up

The predecessor to Workload Identity was AAD Pod Identity, now deprecated in favor of the newer OIDC-federation-based Workload Identity approach — mentioning this shows current knowledge rather than outdated familiarity, similar to how EKS's IRSA itself replaced older, less secure patterns like manually injecting AWS credentials as Kubernetes Secrets.

Say this in interview

"AKS Workload Identity and IRSA solve the identical problem the identical way — OIDC federation exchanging a short-lived Kubernetes token for a scoped cloud identity token, avoiding both broad node-level permissions and any static credentials in the cluster. If I were designing a multi-cloud platform, I'd treat this as one consistent security pattern to enforce everywhere, not two separate mechanisms to reason about independently."

Load Balancing & Ingress

Azure's equivalent to the AWS Load Balancer Controller
AWS: AWS Load Balancer Controller → ALB / NLB ↔ Azure: Application Gateway Ingress Controller (AGIC) → Azure Application Gateway / Azure Load Balancer
Service type=LoadBalancerProvisions a standard Azure Load Balancer — the direct parallel to a Kubernetes Service provisioning an AWS NLB: Layer 4, simple, high-throughput.
Ingress objects, via AGICThe Application Gateway Ingress Controller watches Ingress resources and configures an Azure Application Gateway — Layer 7, path/host-based routing, with built-in Web Application Firewall (WAF) support — the direct parallel to Ingress provisioning an AWS ALB via the AWS Load Balancer Controller.
A genuine Azure-side advantage worth naming

Application Gateway's built-in WAF integration is more first-class/native than the equivalent AWS pattern (which typically layers AWS WAF onto an ALB as a separate, additional configuration step) — a fair, specific point of comparison to raise if asked directly which platform's ingress story is stronger for security-sensitive public-facing workloads.

Say this in interview

"AGIC-to-Application-Gateway is the direct parallel to the AWS Load Balancer Controller provisioning an ALB from an Ingress resource — same Layer 7 routing model. If pushed on a real difference, I'd point to Application Gateway's more integrated WAF story compared to bolting AWS WAF onto an ALB as a separate step — a small but genuine Azure-side advantage for public-facing, security-sensitive ingress."

Storage — Azure Disk & Azure Files CSI Drivers

The same EBS-vs-EFS decision, Azure-flavored
Azure Disk CSI DriverDirect parallel to EBS CSI — provisions a block-storage disk attached to exactly one node at a time. Right for a single Pod needing durable storage (a database).
Azure Files CSI DriverDirect parallel to EFS CSI — a network file share multiple Pods across multiple nodes can read/write concurrently. Right when storage needs to be genuinely shared.
Say this in interview

"Azure Disk to EBS, Azure Files to EFS — same decision framework applies unchanged: does exactly one Pod need it, or do multiple Pods need concurrent shared access. The single-node-attach constraint on Azure Disk creates the same StatefulSet rescheduling consideration as EBS does on EKS."

Autoscaling

Cluster Autoscaler is the shared default here — Karpenter's Azure story is still catching up
AKS Cluster AutoscalerFunctionally identical to EKS's Cluster Autoscaler — scales a defined Node Pool (AKS's equivalent of an ASG) up/down based on unschedulable Pods. This is still the standard, default autoscaling approach on AKS.
Karpenter on AzureKarpenter (the just-in-time, right-sized provisioner covered on the EKS page) has an Azure provider, but it's meaningfully less mature and less commonly used in production on AKS than on EKS — worth knowing it exists, but Cluster Autoscaler remains the pragmatic default choice on Azure today, unlike on AWS where Karpenter is increasingly the recommended default for new clusters.
Say this in interview

"On EKS I'd lean toward Karpenter for new clusters given how mature it's become there — on AKS, I'd stick with Cluster Autoscaler as the pragmatic default today, since Karpenter's Azure provider hasn't reached the same maturity or adoption level yet. That's a genuine, current platform difference worth naming rather than assuming feature parity across clouds."

AKS vs Container Apps vs ACI

The same "do you actually need Kubernetes" decision as EKS vs ECS
AWS: EKS vs ECS vs self-managed ↔ Azure: AKS vs Container Apps vs ACI
AKSFull Kubernetes — right when you need the K8s ecosystem, multi-cloud portability, or existing team expertise, exactly the same reasoning as choosing EKS over ECS.
Azure Container AppsAzure's simpler, higher-abstraction serverless container platform (built on Kubernetes/KEDA under the hood, but fully hidden from you) — the closer parallel to ECS: less operational complexity, no Kubernetes concepts to manage, right for teams that don't need K8s directly.
Azure Container Instances (ACI)The simplest option — run a single container or container group with no orchestration layer at all, comparable to AWS Fargate used standalone without ECS/EKS on top. Right for simple, isolated, short-lived workloads.
Say this in interview

"This mirrors the EKS-vs-ECS decision closely — Container Apps is Azure's ECS-equivalent answer for teams that want containers without taking on Kubernetes directly, and ACI is closer to standalone Fargate for simple, isolated workloads. I'd apply the identical judgment: don't default to the Kubernetes option just because it's the most fully-featured — match the platform to whether the team actually needs K8s' ecosystem and portability."

Rapid Recall Drill

Free tier vs Standard tier on AKS — what's the real difference?
Standard tier adds a financially-backed SLA and higher scale limits — the tier you'd choose for any production workload, roughly matching EKS's control plane always being paid and SLA-backed.
What AKS concept has no direct EKS equivalent?
The mandatory System Node Pool — AKS requires isolating cluster-critical add-ons onto a dedicated pool, separate from application workloads.
Azure CNI vs Kubenet — which avoids VNet IP exhaustion?
Kubenet — Pods get overlay-network IPs, not real VNet IPs, at the cost of an extra NAT hop and reduced feature support.
What's the direct Azure equivalent of IRSA?
AKS Workload Identity — same OIDC federation mechanism, exchanging a short-lived K8s token for a scoped cloud identity token.
Which cloud's ingress controller has more native WAF integration?
Azure — Application Gateway's WAF is more first-class than layering AWS WAF onto an ALB as a separate step.
Is Karpenter equally mature on both clouds?
No — mature and increasingly default on EKS; the Azure provider exists but is less mature, so Cluster Autoscaler remains the pragmatic AKS default.
Azure's equivalent to choosing ECS over EKS?
Choosing Azure Container Apps over AKS — simpler, no Kubernetes concepts exposed, right when a team doesn't need K8s' ecosystem/portability.
