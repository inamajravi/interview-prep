Microservices Reference Architecture

13 services, one realistic e-commerce + payments platform — built specifically to answer "how do dependent services keep working when something else is down," with an explicit distinction between what's allowed to degrade and what absolutely cannot.

Say this in interview

"I'd deliberately design each service around a single business capability with its own data store — no shared database between services — which is what actually makes independent deployment and independent failure possible in the first place. The Sanctions Screening service being isolated from Payment, specifically, isn't incidental — it needs its own scaling profile and its own compliance boundary."

Communication Patterns

Sync vs async isn't a style choice — it's decided by whether the caller needs to know the outcome before proceeding
Synchronous (REST/gRPC) — used forOrder → Inventory (must know stock is reserved before proceeding), Order → Payment (must know the charge succeeded), Payment → Sanctions Screening (must know the transaction is clear before settling funds). All three are cases where the caller genuinely cannot proceed without the answer.
Asynchronous (events via SNS/SQS) — used forOrder → Notification, Order → Analytics, Catalog → Search indexing, any "→ Review/Rating" display calls. None of these need to block the caller — the checkout succeeding doesn't depend on the confirmation email being sent yet.

Internal service-to-service synchronous calls use gRPC rather than REST/JSON specifically for the high-performance requirement — binary protobuf serialization and HTTP/2 multiplexing measurably reduce latency over JSON-over-HTTP/1.1 for high-volume internal traffic, while the public-facing API Gateway still exposes REST/JSON externally where broad client compatibility matters more than raw throughput.

Say this in interview

"I decide sync vs async by one question: does the caller need the answer before it can correctly proceed? If yes — reserving inventory, charging a card, clearing a sanctions check — it's synchronous, because pretending otherwise just moves the problem somewhere less visible. If no — a confirmation email, an analytics event — it's async by default, because there's no reason to couple the caller's success to it."

The Core Principle: Hard vs Soft Dependencies

This is the actual answer to "how do services keep working when a dependency is down" — the honest answer is: not all of them do, and that's correct

The instinct "every service should have a fallback so nothing ever fails" is wrong for this domain, and saying so explicitly is a stronger interview answer than pretending otherwise. Some dependencies are HARD — the calling service cannot safely proceed without them, and the correct behavior is to fail the request cleanly (fail-closed). Others are SOFT — the calling service can degrade gracefully and continue without them (fail-open).

Hard dependency examplePayment Service calling Sanctions Screening. If Screening is down, Payment Service must not fall back to "skip the check and approve anyway" — that's a compliance and legal failure, not a resilience win. The correct behavior is to hold the transaction in a pending state, retry, and fail the checkout cleanly with a clear "try again shortly" if screening stays unavailable past a timeout.
Soft dependency exampleProduct page calling Review/Rating Service. If Reviews is down, the product page renders completely fine without the reviews section — the core purchase flow was never blocked by a dependency that was never actually required to complete a purchase.
The question that decides which one a dependency is

"If this call silently failed and we proceeded anyway, what's the actual cost?" — if the answer is "a slightly worse user experience" (no reviews, no recommendations, a stale search index), it's soft — degrade gracefully. If the answer is "money moved that shouldn't have, or a sanctioned entity got paid," it's hard — fail closed, every time, no exceptions, regardless of how good the circuit breaker's fallback story sounds in the abstract.

Say this in interview

"I explicitly classify every dependency as hard or soft before designing its failure behavior — it's the single most important architectural decision in a fault-tolerant system, and it's also the one place where 'just add a circuit breaker with a fallback' is actually the wrong answer if applied blindly. A circuit breaker's fallback for a hard dependency should be 'fail the request cleanly,' not 'proceed with a default value' — proceeding with a default is exactly correct for a soft dependency and exactly wrong for a hard one."

Fault Tolerance & Fallback Matrix

Every real dependency in the diagram, what happens if it's down, and which pattern from the Resilience Patterns page handles it
Caller → DependencyTypeIf the Dependency Is DownPattern Used
Order → Inventory HARD Circuit breaker opens after threshold failures; checkout fails cleanly with "try again" rather than accepting an order for stock that can't be confirmed reserved. Circuit breaker + timeout
Order → Payment HARD Retry with exponential backoff for transient failures; circuit breaker opens for sustained outages; order held in "payment-pending" state, never silently marked paid. Retry + circuit breaker + Saga compensating step
Payment → Sanctions Screening HARD Never falls back to skipping the check. Transaction held, bounded retry, and a clean failure if Screening stays unavailable past the timeout — fail-closed by design. Fail-closed + bounded retry, no fallback path
API Gateway → Identity (token validation) HARD (mitigated) Gateway caches the Identity Service's public signing keys (JWKS) locally — most token validations don't need a live call at all, so brief Identity outages barely register. Local JWKS cache — turns a hard dependency into one that tolerates real outages
Order → Notification SOFT Fire-and-forget via SQS. Checkout completes regardless; the notification is delivered whenever the service recovers — eventually consistent, never blocking. Async decoupling via message queue
Catalog → Search (indexing) SOFT Search index falls behind if Search/indexing is down; Catalog's own DB-backed basic query still works as a degraded fallback for product lookups. Graceful degradation to a simpler direct query
Any Service → Redis Cache SOFT Cache-aside pattern falls back to reading directly from the database — slower, but fully functional. Cache is treated as a pure optimization, never a hard requirement. Cache-aside with DB fallback
Product Page → Review/Rating SOFT Page renders fully without the reviews section; a short timeout plus bulkhead isolation ensures a slow Review service can't tie up threads needed for the actual purchase flow. Bulkhead + timeout + UI-level graceful degradation
Order → Shipping/Fulfillment HARD (deferred) Order is accepted and payment/screening already cleared — shipping dispatch is queued asynchronously rather than blocking checkout, with retry until Fulfillment confirms receipt. Async queue with guaranteed delivery — hard requirement, soft timing
Say this in interview

"The Fulfillment row is a good example of a nuance beyond simple hard/soft — shipping dispatch genuinely must happen eventually, so it's not optional the way reviews are, but it doesn't need to happen synchronously within the checkout request either. I'd call that a hard requirement with soft timing — queued reliably, retried until confirmed, but never blocking the customer's checkout response."

Checkout Flow — Failure Walkthroughs

Same request, three different failure scenarios, traced step by step
Scenario A: Happy path
1. Client → API Gateway
Request authenticated via cached JWKS — no live Identity Service call needed.
2. Order Service starts the checkout Saga
Calls Inventory (reserve stock) → Payment (charge card) → Payment calls Sanctions Screening (clear the transaction) → all synchronous, all succeed.
3. Order confirmed, response returned to client
Order Service publishes an "OrderPlaced" event.
4. Async fan-out
Notification Service sends confirmation email; Analytics records the event; Fulfillment picks up the shipping job — none of this delays the response the customer already received.
Scenario B: Review Service is down (soft dependency)
Impact
Zero impact on checkout. The product page the customer browsed earlier simply rendered without a reviews section — a bulkhead-isolated timeout ensured that slow/down Review calls never consumed resources the checkout flow needed. The customer completes their purchase with no idea anything was degraded.
Scenario C: Payment Service is down (hard dependency)
1. Order Service calls Payment
Fails — retried twice with exponential backoff, both fail. Circuit breaker opens after the threshold.
2. Order held, not silently failed or silently succeeded
Order Service's Saga executes the compensating step: the Inventory reservation from step earlier is released (so stock isn't held hostage by a stuck order), and the order is marked "payment-failed — please retry."
3. Customer sees a clear, honest error
Not a silent failure, not a false success — a real "something went wrong, please try again" with the reservation correctly released behind the scenes.
Scenario D: Sanctions Screening Service is down (hard dependency, zero fallback)
1. Payment Service attempts the charge
Card authorization succeeds — but Payment Service will not settle/capture funds until Screening clears the transaction.
2. Screening call fails, bounded retry also fails
Unlike the Payment scenario above, there is no acceptable fallback here — Payment Service does not proceed with settlement.
3. Transaction held in "pending-screening," authorization voided if it exceeds a bounded window
The customer sees "your order is being processed" rather than either a false success or a confusing hard failure — and no funds are ever captured without a clean pass through Screening. This is the one path in the entire system with genuinely zero fallback, by design.
Say this in interview

"Scenario D is the one I'd lead with if asked to demonstrate real fault-tolerance thinking, not just pattern-matching 'add a circuit breaker everywhere.' The sophisticated answer isn't that every dependency has a graceful fallback — it's knowing precisely which one dependency in the entire system is not allowed to have one, and designing its failure mode to be safe by construction rather than convenient."

High-Performance Techniques

Where the real latency and throughput wins come from across this architecture
Read replicas + cache-aside (Redis)Catalog and Search reads are the highest-volume, most read-heavy traffic in the system — serving them from replicas and a cache layer keeps the primary write databases free for the transactional paths (Order, Payment) that actually need strong consistency.
gRPC for internal service-to-service callsBinary protobuf + HTTP/2 multiplexing meaningfully reduces latency over JSON/REST for the high-volume internal traffic between Order, Inventory, and Payment — while the Gateway still exposes REST externally for broad client compatibility.
CQRS on Order ServiceOrder writes (placing an order) go through the full Saga and validation path; order history/dashboard reads are served from a separate, denormalized read model — exactly the CQRS pattern from the Architecture page, applied because write and read shapes here genuinely diverge.
Async everything that doesn't need to blockNotification, Analytics, and Search indexing are entirely event-driven — moving them off the synchronous critical path is as much a performance win as a resilience one, since the checkout response time no longer includes any of their latency at all.
Say this in interview

"A lot of the performance story here is really the same decision as the fault-tolerance story, seen from a different angle — moving Notification, Analytics, and Search off the synchronous path doesn't just protect checkout from their outages, it also removes their latency from the checkout response time entirely. Resilience and performance point in the same direction more often than people expect."

Rapid Recall Drill

What's the single question that decides if a dependency is hard or soft?
"If this call silently failed and we proceeded anyway, what's the actual cost?" — a worse UX means soft; money moving incorrectly or a compliance breach means hard.
Why doesn't Payment Service fall back to "skip screening and approve anyway" when Sanctions Screening is down?
That's not resilience, it's a compliance failure — the correct behavior is fail-closed: hold the transaction, bounded retry, then a clean failure, never a silent bypass.
How does the API Gateway keep validating tokens even if Identity Service is briefly down?
It caches Identity's public signing keys (JWKS) locally — most validations don't need a live call, turning a hard dependency into one that tolerates real outages.
What happens to an Inventory reservation if Payment subsequently fails?
The Saga's compensating step releases the reservation — this is exactly the Saga pattern from the Architecture page: local transactions plus explicit compensating actions on failure.
Why is Review/Rating a soft dependency but Fulfillment is not, even though both are "downstream" of checkout?
Reviews never need to happen at all for a valid purchase — pure UX. Shipping dispatch genuinely must happen eventually — it's a hard requirement, just with soft (asynchronous) timing, not a true soft dependency.
